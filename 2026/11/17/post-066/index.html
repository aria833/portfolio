IDOR | 為什麼有些房卡可以隨便開別人的房間？

UUID IDOR 資安 OWASP

在 UUID 的文章中，我們聊過為什麼軟體開發不用傳統的流水號（如 1, 2, 3），而是改用 UUID 來作為資料的識別碼。其中一個最關鍵的原因，就是為了 防範網頁開發中的資安漏洞–IDOR。

什麼是 IDOR？

IDOR 全名為 Insecure Direct Object Reference（中文通常翻譯為：不安全的直接物件參照）。

這個名稱雖然聽起來很學術，但是我們可以想像今天去住飯店時，拿到的 房卡 來做比喻：

  • 正常的系統：櫃檯給你一張房卡，上面寫著房號 101。你刷這張卡只能開 101 房的門，絕對打不開別人的房間。

  • 有 IDOR 漏洞的系統：櫃檯雖然把卡給了你，但房門的鎖完全沒檢查身分。你只要把房卡上的號碼改成 102或103，就能直接打開陌生人的房間，甚至可以把房內的東西都拿走。

IDOR 是怎麼發生的？

假設今天你登入了自己的會員中心，想要查看自己的訂單與個人私密紀錄，瀏覽器向伺服器發送了這樣一個 API 請求：

GET /api/orders?user_id=1005

伺服器回傳了屬於 1005 號會員的資料。但如果後端工程師忘記在程式碼裡檢查「發出這個請求的人，到底是不是 1005 號的本人」，就會發生嚴重的問題：

1. 輕易篡改

有心人士只要打開瀏覽器的開發者工具（F12），或是直接把網址列的數字改成：
GET /api/orders?user_id=1006

2. 資料看光光

因為伺服器完全沒有做權限驗證（Authorization），它看到有請求進來，就毫無防備地把 1006 號會員的信用卡號、住址、私密訂單全部回傳給了你。

這種不需要任何高級駭客技巧、只要 改改數字就能偷看別人資料 的特性，讓 IDOR 長期穩居 OWASP Top 10（十大 Web 應用程式安全風險） 的熱門排行。

OWASP：Open Web Application Security Project

怎麼防範 IDOR 漏洞？

雖然使用 UUID 可以當作第一道防線，但要真正消滅 IDOR，核心原則只有一個：

「永遠不要信任前端傳來的身分或 ID，後端一定要嚴格檢查：『這個登入的使用者，到底有沒有權限讀取或修改這筆資料』。」

確實驗證 Token / Session

在每次收到請求時，後端必須從登入憑證中解析出「目前發起請求的人究竟是誰」。

核對歸屬權

去資料庫或權限系統核對：「這筆資料是不是他的？如果不是，直接拒絕並回傳 403 Forbidden。」
