命名規範｜程式碼中常見的變數與函式命名規範

命名規範

不知道大家有沒有看過那種檔案名稱寫著「最終版」、「最終版_v1」、「最終版_v2」的檔案？平時可能覺得影響不大，但真正要找檔案或協作時，往往會感到混亂、無從下手。

在程式碼的世界裡，命名不規範有時候只是看起來不整齊，但有時候卻會直接導致程式報錯。例如我自己曾經在購買網域時，沒注意到某些字元無法使用，導致搜尋時找不到而感到困惑；又或者之前在 語系切換｜使用 data-i18n 實現多國語系的流暢切換 中提到在 data-i18n 屬性中用了 - 導致報錯。

因此，這篇文章要來整理程式碼中常見的命名規範，之後可以避開報錯，並且讓專案看起來更整齊、更好維護。

駝峰式命名（Camel Case）

程式語言中最常見的風格之一，透過大小寫的變化來區隔不同的單字。

1. 小駝峰式（Camel Case / lowerCamelCase）

  • 規則：第一個單字首字母小寫，後續每個單字首字母大寫，單字之間沒有任何分隔符號。

  • 範例：userName、totalAmount

  • 應用場景：在 JavaScript、Java、TypeScript 等語言中，常被廣泛應用於變數、函式（Function）與屬性的命名。

2. 大駝峰式（Pascal Case / UpperCamelCase）

  • 規則：所有單字的首字母皆大寫，也被稱為帕斯卡命名法。

  • 範例：UserProfile、ShoppingCart、DatabaseConnection

  • 應用場景：在多數物件導向語言中，是「類別（Class）」、「介面（Interface）」或現代前端框架中「元件（Component）」標準的命名方式。

底線（Snake Case）

利用底線 _ 作為單字之間的分隔符號，依據字母的大小寫又可細分為以下兩種：

1. 小寫底線（Snake Case / lower_snake_case）

  • 規則：所有字母皆為小寫，單字之間使用底線連接。

  • 範例：user_name、total_amount、max_retry_count

  • 應用場景：Python 語言中變數與函式的官方建議風格；此外，在關聯式資料庫中，資料表（Table）與欄位（Column）的命名也普遍採用此種風格。

2. 大寫底線（SCREAMING_SNAKE_CASE）

  • 規則：所有字母皆為大寫，單字之間使用底線連接。

  • 範例：MAX_CONNECTIONS、DEFAULT_TIMEOUT、API_KEY

  • 應用場景：通常專門用來宣告「全域常數（Constants）」或是系統的「環境變數（Environment Variables）」，提醒開發者這是不可輕易異動的值。

短橫線命名（Kebab Case / dash-case / spinal-case）

  • 規則：所有字母皆為小寫，單字之間使用連字號（短橫線 -）連接，形狀像烤肉串上的肉塊。

  • 範例：user-profile、main-navigation、submit-button

  • 應用場景：因為在多數程式語言中 - 會被解析為減號，所以此命名法極少用於變數或函式。它主要用在網頁前端領域，例如 CSS 類別名稱、網址路徑（URL slugs），以及前端框架（如 Vue、React）的檔案命名與 HTML 屬性中。

其他特殊或歷史命名法

除了上述三大主流外，歷史上與特定領域還有幾種較為少見或特殊的風格：

匈牙利命名法（Hungarian Notation）

  • 規則：在變數名稱的最前方，加上代表「資料型態」或「用途」的小寫前綴。

  • 範例：strName（字串）、iCount（整數）、bIsValid（布林值）

  • 應用場景：早期 C 語言或 Windows API 開發較常使用。現代軟體工程中因為 IDE 會自動提示型態，若強制使用反而容易導致名稱冗長，故較少被推崇。

扁平命名法（Flat Case）

  • 規則：將所有單字全部小寫連在一起，不使用任何大小寫區分或符號。

  • 範例：username

  • 應用場景：由於可讀性極差，現代程式碼中幾乎不採用，多見於非常簡單的常數或特定的設定檔中。

結語

選擇哪一種命名方式，往往取決於所使用的 程式語言生態系（例如 Python 用 snake_case，JavaScript 用 camelCase）以及 團隊內部的規範。

無論使用哪一種，最核心的原則是「保持一致性」與「易懂性」。
